# 桌面端智能体平台（Pi 内核）设计文档

- 日期：2026-08-22
- 状态：待评审（spec）
- 主题：以 `earendil-works/pi` 为 Agent 内核的 2B 桌面端智能体产品

## 1. 背景与目标

本产品是一款面向 2B 场景的桌面端智能体工具，以
[earendil-works/pi](https://github.com/earendil-works/pi) 作为 Agent 内核，用于
水泥厂工艺流程、合同审核、采购市场预判等领域。

Pi 是 TypeScript/Bun 的 monorepo，内核为 `pi-agent-core`（Agent 循环 + 工具调用 +
状态管理），`pi-ai` 统一多模型 API。它原生提供 SDK 模式与 RPC 模式（JSON over
stdin/stdout），天然适合被桌面应用嵌入；但它刻意未提供权限系统、沙箱、sub-agent、
MCP、plan mode、后台 bash 等能力，这些在 2B 场景下需要自建。

本产品是一个**配置驱动的标准底座**：一套代码，通过每客户的“配置包”（skills 组合 +
流程组合 + 页面组合）实例化成不同形态。垂直产品先行，首个 pilot 为**合同审核智能体**。

## 2. 需求与已确认决策

1. **定位**：配置驱动的标准底座，一套代码 + 每客户“配置包”（skills/流程/页面）实例化
   成不同形态；垂直产品先行。
2. **流程**：先做轻量编排，抽象成可插拔引擎接口，后续接 Dify 或自建完整引擎。
3. **部署**：Windows 优先、尽量跨平台；私有化本地模型为主 + 可切云端。
4. **界面**：混合双模式——应用首页（结构化页面）+ 对话工作台，均可配置组合。
5. **配置作者**：开发团队用 DSL/文件写复杂配置，客户/管理员应用内做轻量开关与参数调整。
6. **集成**：文档、企业系统、外部数据、本地工具全要；企业系统可写但必须人工审批。
7. **多 Agent**：先单 Agent，抽象“执行单元”，未来可平滑升级多 Agent。
8. **安全合规**：强合规——SSO/LDAP/AD + RBAC + 集中审计 + 数据不出厂 + 可对接等保/ISO。
9. **Pilot**：合同审核智能体。

## 3. 方案选型

团队现状：主要靠 AI（Codex 等）或少量自研来建设，团队本身偏产品/业务，无 Rust 储备。
因此选型原则是“最主流、最少运维、单语言、AI 最熟悉”，而非“最轻量或最炫”。

### 方案 2（选定）：Electron 壳 + Pi RPC 子进程（进程隔离）

- 桌面壳用 Electron（TypeScript），主进程 spawn 一个 Pi 子进程，通过 Pi 自带的
  JSON-RPC（stdio）通信；渲染层用 React 做可配置页面 + 对话工作台；审批门和审计放在
  Electron 主进程。
- 优点：全链路一门语言（TS/Node/Bun），AI 对 Electron+React 生态最熟；Pi 的 RPC 模式
  是一等公民；Agent 与 UI 进程隔离——崩溃不拖垮界面、可独立重启/升级/沙箱，对应强合规。
- 缺点：比内嵌多一点进程管理 + IPC 序列化的复杂度（可控）。

### 方案 1（未选）：Electron 内嵌 Pi SDK（最简）

- 主进程直接 `import` `pi-agent-core`，Agent 跑在进程内。
- 优点：最少动件、最快跑通 MVP。
- 缺点：Agent 循环和 UI 同进程，崩溃互相影响；进程隔离弱，与强合规冲突，后期补隔离需重构。

### 方案 3（未选）：Tauri 壳 + Pi sidecar

- Tauri（Rust）做壳，Pi 作为 sidecar 子进程。
- 优点：体积最小、内存最低、Rust 安全基线强。
- 缺点：需 Rust + Bun 两套运行时/两门语言；团队无 Rust 储备，AI 维护 Rust 侧成本高、风险大。

## 4. 总体架构

### 4.1 运行时拓扑（3 进程，2 条通道）

```text
┌──────────────────────────────────────────────────────────┐
│ Renderer（React，沙箱化）                                  │
│  业务页面(可配置) + 对话工作台 + 审批弹窗 + 审计视图          │
└───────────────▲─────────────────────────────┬────────────┘
                │ ① Electron IPC（typed，contextBridge）│
┌───────────────┴─────────────────────────────▼────────────┐
│ Electron Main（控制层/壳，Node+TS）                        │
│  配置包加载/校验/切换 · 会话 · 模型路由 · 审批门 · 审计 ·    │
│  身份/RBAC · 密钥管理 · Pi 子进程生命周期                    │
└───────────────▲─────────────────────────────┬────────────┘
                │ ② Pi JSON-RPC（stdin/stdout 事件流）│
┌───────────────┴─────────────────────────────▼────────────┐
│ Pi Agent 子进程（Bun/Node，内核，基本不改）                  │
│  pi-agent-core 循环 · pi-ai 多模型 · tools/skills · 会话树 · │
│  压缩 · 只读连接器工具 · “写”仅作为提议请求发往 Main          │
└──────────────────────────────────────────────────────────┘
```

要点：
- Renderer 永远不碰密钥和系统权限。
- Main 是“可信但最小权限”的控制层。
- Pi 子进程专注 Agent 循环，**不含写原语**（见第 7 节的“提议—执行分离”）。

### 4.2 逻辑组件

1. **配置包系统**：版本化目录（JSON + TS DSL），定义“应用形态”：启用哪些 skills、
   页面 schema、流程定义、连接器、权限、模型路由、主题。可加载/校验/热切换。
2. **模型路由层**：包一层 `pi-ai`，按配置 + 任务选本地/云端模型，支持降级切换。
3. **连接器层**：A 文档/知识库、B 企业系统、C 外部数据、D 本地工具；每个连接器 =
   类型化工具 + 认证 + 读写语义 + 沙箱边界；写操作标记“需审批”。
4. **审批门**：所有写/高风险操作的人工确认通道，支持超时自动拒绝，全程留痕。
5. **审计与合规**：追加式日志（身份/动作/工具调用/载荷摘要/审批决定/模型路由），
   可导出，预留等保/ISO 对接。
6. **身份与 RBAC**：MVP 本地账号 + 角色；后续接 SSO/LDAP/AD。
7. **会话管理**：复用 Pi 的会话树，按“业务实例”归组。
8. **页面组合引擎 + 对话工作台**：声明式 UI + 绑定到会话/skills/流程的聊天工作台。
9. **打包与更新**：Windows 优先，跨平台；离线安装；配置包作为可安装的“应用包”。

### 4.3 技术栈

- 壳：Electron（稳定版）+ electron-builder。
- 渲染：React + TypeScript + Vite；**无头组件原语（Radix / shadcn 风格）+ 自有皮肤层**；
  页面用“组件注册表 + JSON schema 驱动”渲染。
- Pi 子进程：Bun（或 Node）+ `pi-agent-core` + `pi-ai`，走 Pi 原生 JSON-RPC。
- 模型：扩展 `pi-ai` 接入 Ollama/vLLM（OpenAI 兼容本地端点）+ 云端。
- 审计：MVP 用 SQLite（WAL）追加写 + 导出；预留集中采集。
- 身份：MVP 本地账号；预留 SSO/LDAP/AD 接口。

### 4.4 仓库结构

```text
apps/desktop/          Electron 壳 + React 渲染层
packages/config/       配置包 schema、加载、校验
packages/connectors/   A/B/C/D 连接器（每个是独立包）
packages/approval/     审批门 + 审计
packages/agent-host/   Pi 子进程封装（RPC client + 事件流）
packages/model-router/ 模型路由
packages/theme/        主题/设计系统（一等交付物）
skills/                内置 skills（合同审核等）
profiles/              示例配置包（合同审核 pilot）
```

## 5. 配置包系统

一个配置包定义“应用形态”，是 dev 侧交付的基本单元，版本化、可校验、可继承、可审计。

### 5.1 目录结构（示例：合同审核）

```text
profiles/contract-review/
  manifest.yaml          # 版本、依赖、继承、模型路由策略
  agent/
    skills.yaml          # 启用哪些 skills + 参数
    tools.yaml           # 启用哪些连接器工具
    prompts/             # system prompt、报告模板等
    workflow.yaml        # 流程定义
  ui/
    pages/*.json         # 页面 schema（布局/组件/数据绑定）
    theme.yaml           # 主题（一等交付物）
  security/
    roles.yaml           # 角色 → 可见页面/可用工具/skills
    approval.yaml        # 哪些操作强制走审批
```

### 5.2 关键设计决策

1. **配置分层**：dev 交付的 profile 是不可变基线（版本化 + 校验 + 哈希签名，防篡改）；
   管理员在应用内的开关/参数调整存成独立 delta，运行时“基线 + delta”叠加生效。
   基线可整体升级，客户轻量改动不被覆盖。
2. **继承与组合**：profile 可 `extends` 一个基线再覆盖局部（如
   `contract-review-base` → `contract-review-customerA` 只改连接器地址、阈值、主题、启用项）。
3. **切换边界（守护 prompt 缓存）**：切换 profile / 技能组合 / 工具集只发生在新建
   会话/业务实例时，绝不在进行中的会话里改，避免破坏模型前缀缓存、让成本翻倍。

## 6. 流程编排层

对应决策 2：先轻量编排，接口可插拔。

### 6.1 统一接口（引擎边界）

```ts
interface WorkflowRunner {
  run(def: WorkflowDef, ctx: RunContext): AsyncIterable<WorkflowEvent>;
}
// 事件：step_started / step_completed / tool_call / approval_required /
//       workflow_completed / workflow_failed …
```

- **默认实现 `LinearRunner`**：顺序执行若干“能力单元”，支持简单输入引用和分支条件，
  以及“人工步骤”。覆盖 pilot 的“读文件→条款抽取→风险比对→生成报告→人工复核”。
- **未来引擎当 provider 接入**：Dify 或自建完整引擎只要实现 `WorkflowRunner`，UI 就能
  用统一方式展示结果。

### 6.2 流程定义（示例）

```yaml
workflow:
  version: 1
  engine: linear
  steps:
    - { id: load,    type: tool,  ref: connectors.document.read }
    - { id: extract, type: skill, ref: contract.clause_extract, inputs: { from: load } }
    - { id: compare, type: skill, ref: contract.risk_compare,   inputs: { from: extract } }
    - { id: report,  type: llm,   template: report,             inputs: { from: [extract, compare] } }
    - { id: review,  type: human,                                inputs: { from: report } }
```

### 6.3 执行单元抽象（为多 Agent 铺路）

最小的可调度单元是“能力单元”：`tool / skill / llm / human`。当前由单个 Agent 按线性
顺序调度；未来换多 Agent 调度器时，能力单元原样复用。

### 6.4 两种触发方式（对应双模式 UI）

- 结构化页面点“开始审核”→ 直接跑 workflow（每个 skill/llm 步骤内部调 Pi）。
- 对话工作台自然语言 → Agent 主导，把“跑某个 workflow”当工具按需调用。

## 7. 连接器层 + 审批门 + 安全合规

### 7.1 连接器层

四类连接器（A 文档/知识库、B 企业系统、C 外部数据、D 本地工具）收敛为同一接口，
每个连接器是独立包，注册一批类型化工具到 Pi。

```ts
interface Connector {
  id: string;
  tools: ToolDef[];
  init(cfg): Promise<void>;
}
interface ToolDef {
  name: string;
  description: string;
  params: JSONSchema;
  sideEffect: 'read' | 'write' | 'high-risk';
  handler(args, ctx): Promise<Result>;
}
```

- 每个工具声明**副作用等级**：`read` 免审批，`write` 需审批，`high-risk` 需审批且可能
  二次确认。审批门在 `handler` 执行前拦截。
- **沙箱分阶段**：MVP 用“连接器最小权限 + 白名单 + 审批 + 审计”兜底；后续对 B/D 类做
  硬隔离（受限子进程/容器/微 VM，参考 Pi 的 containerization 模式）。
- Pilot 连接器只需：文档解析（PDF/Word/Excel）、法规知识库 RAG、报告导出（Word/PDF）；
  ERP/MES/DCS 留接口、下一阶段再接。

### 7.2 审批门：写操作的“提议—执行分离”

安全硬约束：**批准决定与写执行由 LLM 之外的确定性代码强制；LLM 只能“提议”，永远不能
“授权”或“执行”一个写操作。** 批准决定绝不能依赖 LLM 的解读来执行。

- **读工具**跑在 Pi 子进程（无副作用）。
- **写/高风险工具在 Pi 里没有写原语**：Pi 只暴露“提议工具”，调用时把“做什么 + 参数”
  冻结成一个写请求发往 Main；真正执行写在 **Main 侧的确定性连接器执行器**，它只读
  Main 里权威的审批决定来放行/阻止。
- **“批准/中止”不是一条让 LLM 去理解的文本**，而是 Main 里的权威状态（批准了哪条提议、
  参数是什么）。执行器直接读该状态，LLM 无法篡改、无法“把中止读成批准”。
- **拒绝 = 直接不写，没有第二条路**；即使 Agent 幻觉误以为批准，在 Pi 进程里也找不到
  可执行的写能力。
- **参数在提议时冻结**：批准后执行的是提议时定格的操作和参数，LLM 无法事后替换。

写操作数据流：

1. Agent（Pi）决定“改合同状态为已复核”→ 调用提议工具，参数冻结。
2. 提议发到 Main → 审批门按 RBAC 弹窗给用户。
3. 用户批准/拒绝 → 决定与提议参数以权威状态存入 Main，并写审计。
4. Main 侧确定性执行器读该状态：批准 → 用连接器隔离凭证、按冻结参数执行；拒绝 → 不执行。
5. 执行结果（权威）回写 UI 与审计；给 Pi 的只是信息性结果。

残余风险堵漏：即便 LLM 在文字里“谎报成功”，UI 也不信任 LLM 叙述，只展示 Main/审计里
的权威状态（“已拒绝/未执行”）。权威状态是唯一事实源。

### 7.3 审批门（统一通道）

同时接收两类请求：连接器写操作的“自动审批”，和流程 `human` 步骤的“显式复核”。

- 审批请求内容：操作描述、目标系统、载荷（大数据只传摘要）、风险等级、来源上下文。
- 策略（来自 `approval.yaml` + RBAC）：哪些操作必须审批、谁能批（按角色）、超时自动拒绝、
  高风险二次确认。
- 失败安全：无人值守/超时一律自动拒绝并审计。

### 7.4 安全与合规（分阶段，接口先留好）

MVP（pilot 阶段）：

- 本地账号 + 角色 RBAC（角色 → 可见页面/可用工具/可批事项）。
- 追加式审计日志（SQLite WAL，本地，可导出）：身份、动作、工具调用、载荷摘要、审批决定、模型路由。
- 数据不出厂：默认本地模型 + 本地存储，云端只在显式配置且允许时才用。
- 密钥进 OS 钥匙串（Windows 凭据管理器）或加密存储，绝不明文、绝不暴露给 Renderer。
- 最小权限：Renderer 沙箱化（contextIsolation、无 Node 能力），连接器凭证隔离。

后续企业级（预留接口，不提前实现）：

- SSO/LDAP/AD 身份接入（`IdentityProvider` 接口）。
- 集中审计采集/留存 + 防篡改（哈希链或签名追加）。
- 等保/ISO：访问控制、操作审计、数据分级、备份、安全基线。
- Agent 子进程硬沙箱（容器/微 VM）。

## 8. UI 层 + 错误处理

### 8.1 页面组合引擎（Page Composer）

结构化页面用声明式 JSON schema 描述，由“组件注册表 + 数据绑定”渲染。

- **组件注册表**：固定的类型化 widget（表单、表格、图表、文件上传、动作按钮、文档预览、
  对话面板、审批面板…）。新增 widget = 在注册表加组件，由 dev 扩展，客户不能注入任意代码。
- **页面 schema**（示例）：

```json
{
  "page": "contract-review/home",
  "layout": { "type": "grid", "columns": 2 },
  "widgets": [
    { "id": "upload", "type": "file-upload", "bind": "documents" },
    { "id": "review", "type": "action-button", "action": "run-workflow:contract-review" },
    { "id": "risk",   "type": "table",       "bind": "workflow.result.risk_compare" },
    { "id": "report", "type": "doc-preview", "bind": "workflow.result.report" }
  ]
}
```

- **数据绑定与状态**：Renderer 维护“应用状态”，由 Main 喂数据。**UI 永远以 Main 的权威
  状态为唯一事实源**，LLM 文字叙述只是旁注。
- **安全约束**：页面 schema 必须校验——只能引用注册表内组件和允许的数据绑定，配置包不得
  在渲染层执行任意代码。

### 8.2 主题/设计系统（一等交付物）

“结构”与“表现”分离，同一份页面 schema 可换不同主题。设计师的风格落在独立主题层，
作为配置包的一等部分（`theme.yaml` + `theme/` 目录），与页面 schema 平级。

按还原度递增三档能力：

1. **设计 token**（颜色/字体/间距/圆角/阴影/层级）：CSS 变量或 token 系统承载。
2. **组件皮肤（slot 化）**：widget 暴露语义槽位，主题为槽位提供自定义样式/组件。
3. **整组件替换**：主题提供自定义组件实现，满足同一 widget 契约即可高保真还原。

布局、导航、页面外壳也可由主题定义。边界：设计师改外观，不改 widget 的行为和数据绑定；
特殊交互式可视化（如 3D 工艺流程图）需 dev 新增 widget 类型，但其视觉仍可主题化。

### 8.3 对话工作台

- 绑定 Pi 会话，经 RPC 事件流实时推送。
- 支持流式 token、工具调用状态透明展示（哪个连接器、读还是写、审批状态）、内联审批。
- 支持“打断/追加”两种交互（对应 Pi 的 steering/follow-up）。

### 8.4 审批 UI

弹窗/面板：操作描述、目标系统、载荷（摘要 + 可展开）、风险等级、批准/拒绝 + 意见、
超时倒计时（自动拒绝）；高风险二次确认。

### 8.5 错误处理

- **Agent 层**：Pi 的 API 失败/上下文溢出/压缩失败 → 统一成类型化事件上抛，指数退避重试；
  上下文溢出触发压缩；对用户给出清晰失败信息。
- **连接器层**：读/写失败、凭证过期、网络中断 → 类型化连接器错误；写失败不得部分提交
  （幂等键/事务）；失败也要审计。
- **进程崩溃**：Pi 子进程崩溃/重启 → Main 检测并重启，利用 Pi 会话树恢复会话，UI 显示
  “重连中”。
- **审批错误**：超时/无人值守 → 失败安全拒绝并审计。
- **配置错误**：profile 非法 → 失败关闭（拒绝加载、给出明确错误、回退到上一个已知可用版本）。
- **安全不变量**：被拒绝的写绝不允许执行；任何写尝试都不得跳过审计。
- **可观测性**：结构化日志 + 本地诊断视图（日志/会话/审计，可导出）；无退出遥测，除非显式开启。

## 9. 测试策略

核心原则：**行为契约优先于快照**；安全不变量测试优先级最高。

- **单元测试**（纯逻辑，无 LLM）：配置 schema 校验、`LinearRunner`、RBAC 策略判定、
  审批门决策、模型路由选择、载荷摘要。
- **契约测试（安全不变量为主）**：
  - 被拒绝的写永远到不了连接器执行器；
  - 每次写尝试恰好产生一条审计记录；
  - 配置包不能注入任意代码 / 页面 schema 只能引用已注册 widget；
  - Renderer 无 Node 能力、无凭证访问。
- **集成测试**：
  - 真实 spawn Pi 子进程，测 RPC 生命周期、工具注册、事件流；
  - 连接器用测试替身（mock CMS/ERP），测读与“写被审批门门控”；
  - 用伪造 LLM（会“硬要写”）验证：即使 Agent 疯狂尝试，写仍被确定性执行器挡住。
- **E2E 测试**（Playwright + Electron）：临时 profile 跑通“上传合同 → 跑流程 → 人工
  批准/拒绝 → 生成报告 → 审计落账”。
- **LLM 依赖测试**：无 API key 时跳过（同 Pi 的 test.sh 策略）；多数测试用假 provider /
  录制的响应，保证快速、可复现。

## 10. 部署与打包

- **打包**：electron-builder；Windows 用 NSIS + MSIX（对接 Intune/SCCM 企业分发），
  macOS DMG，Linux AppImage/deb。
- **离线安装**：应用 + 内置 Pi 运行时（Bun/Node）+ 可选 Ollama 本地模型运行时一起离线包；
  模型权重按需另发。
- **配置包分发**：dev 对 profile 签名，应用加载前验签；admin 的 delta 本地存；支持应用内
  签名更新或侧载。
- **模型路由部署**：默认本地（Ollama/vLLM 端点），云端可选，按 profile 配。
- **数据目录**：按用户隔离；敏感数据加密落盘；审计本地 + 可导出。

## 11. MVP 范围与 Pilot 验收

MVP（pilot = 合同审核）：Electron 壳 + Pi RPC 子进程；配置包系统（基线 + delta + 继承 +
验签）；`LinearRunner` + `WorkflowRunner` 接口；连接器只做文档解析（PDF/Word/Excel）、
法规知识库 RAG、报告导出（Word/PDF）；审批门（提议—执行分离，报告导出=写，走审批）；
本地审计（SQLite WAL + 导出）；本地账号 + 简单 RBAC；页面组合 + 对话工作台 + 主题层；
模型路由（本地 + 云端）。

明确不做（留接口，后续再做）：SSO/LDAP/AD、集中审计、等保/ISO 加固；ERP/MES/DCS、
外部数据、本地工具连接器；多 Agent 调度、完整流程引擎（Dify 接入）；硬沙箱（容器/微 VM）；
跨平台打磨（先 Windows）。

Pilot 验收标准：客户装好应用 + 合同审核 profile 后，能“上传合同 → 跑审核流程 → 得到风险
报告 → 对‘导出/写入’操作审批 → 在审计里看到完整留痕”，且被拒绝的写不会发生。
