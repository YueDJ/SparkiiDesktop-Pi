BLOCKING FINDINGS

F4 — Invalid pendingOp identity/control shapes bypass both corpus discovery and truth redaction, so plaintext can survive privacy deletion.
Evidence:
- The schema declares targetId/projectId as strings and mergeIds as a string array (apps/desktop/electron/main/memory/types.ts:13-20), but truth parsing casts any pendingOp object without validating those fields (apps/desktop/electron/main/memory/store.ts:112-123).
- Production addMemory stores the supplied pendingOp wholesale (apps/desktop/electron/main/memory/service.ts:504-525); addMemoriesBatch does the same (apps/desktop/electron/main/memory/service.ts:599-608). Legacy truth can therefore contain invalid structural shapes.
- The collector excludes targetId/projectId/mergeIds solely by key name, without first validating their shape (apps/desktop/electron/main/memory/service.ts:73-88). A target-session pendingOp such as mergeIds: { nested: [secret] } contributes no secret to removedTexts at service.ts:814-824.
- The truth redactor then unconditionally returns those same fields unchanged (apps/desktop/electron/main/memory/store.ts:1096). Thus even when the same secret is known from another target field, a surviving invalid structural value remains plaintext.
Impact: a secret carried only in an invalid/legacy structural field is omitted from the global approval/audit/error/log/chat corpus and can remain in surviving user.json and SQLite. This is the same privacy guarantee as F2, not merely malformed-input handling.
Required repair:
1. Validate each top-level structural field before exempting/preserving it: targetId/projectId must have the appropriate string identity shape and mergeIds must be an array of valid string IDs.
2. Recursively collect and redact invalid structural values; only validated identity metadata may bypass content redaction.
3. Add a real MemoryService regression where the sole target secret is inside an invalid structural shape and a surviving other-session entry/chat/audit carries it; assert raw truth and retained stores no longer contain it.

F5 — Whitespace-only episode topics become a global deletion token and silently corrupt unrelated retained text.
Evidence:
- Production extraction accepts every string in topics and does not trim or reject whitespace-only entries (apps/desktop/electron/main/memory/ops.ts:37-42,79-82); the batch persists those topics at apps/desktop/electron/main/memory/extraction.ts:168-178.
- Privacy normalization filters only text.length > 0 (apps/desktop/electron/main/memory/service.ts:90-92), so a valid topic ' ' survives normalization and is collected verbatim at service.ts:816-823.
- That value is journaled and passed to every global scrubber. Truth redaction performs output.split(value).join('[已删除]') (apps/desktop/electron/main/memory/store.ts:1065-1074); equivalent unconditional replacement is used by audits, errors, chat and logs.
- After these destructive rewrites, privacyDeleteBySession clears the journal and returns success (apps/desktop/electron/main/memory/service.ts:852-858).
Impact: deleting one session with a whitespace-only topic replaces ordinary spaces throughout unrelated memories, pending content, chat inputs, audit payloads and log strings, causing silent cross-session data corruption. Tabs/newlines and other whitespace-only strings have the same class of effect.
Required repair:
1. Treat whitespace-only corpus entries as empty while retaining the original value for non-empty content, so leading/trailing whitespace in real secrets is not lost.
2. Apply the same normalization before journal persistence and in legacy-journal loading.
3. Add a production extraction/appendEpisode regression with topics [' '] and unrelated multiword memory/chat/audit content; verify deletion succeeds without altering unrelated text.
