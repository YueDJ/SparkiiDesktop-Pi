Conclusion
The two original final-review blockers are repaired in the inspected implementation: workflow journal/cleanup is lease-guarded, and IPC transient waiters are per-session arrays keyed by exact waiter object and lease. However, independent inspection found three remaining blocking defects in the same domain: duplicate concurrent acquisition of one session ID corrupts pool ownership/accounting, session-creation failure cleanup can delete/release a same-ID replacement, and the fixed redaction marker can itself preserve a registered secret. Therefore this review cannot approve the domain.

Remaining blocking findings

1. BLOCKING — concurrent acquire of the same session ID creates multiple live owners and inconsistent pool state/event attribution.
Evidence:
- packages/agent-host/src/pi-runtime-pool.ts:153-159 does not reject or coalesce an already-bound sessionId; with spare capacity it starts another cold slot.
- packages/agent-host/src/pi-runtime-pool.ts:319-328 unconditionally assigns slot.sessionId and overwrites bySession.set(sessionId, {client, lease}) for the second slot.
- packages/agent-host/src/pi-runtime-pool.ts:89-104 counts every bound slot in snapshot.active/slots, while 483-485 counts only bySession.size in activeCount(); get() at 386-393 returns only the last mapping.
- packages/agent-host/src/pi-runtime-pool.ts:178-181 filters events without checking bySession ownership, so both same-ID slots can forward events under that ID.
- packages/agent-host/src/pi-runtime-pool.ts:451-455 release finds the first matching slot and deletes the single session mapping, which may belong to the other slot.
- apps/desktop/electron/main/ipc.ts:965-989 has no single-flight guard around ensureOpenSession; two concurrent promptSession calls for one not-yet-open session can both reach pool.acquire after awaiting listPiSessions.
Impact: duplicate runtime processes, activeCount/get/snapshot disagreement, duplicate or cross-process output attributed to one session, and an orphaned/incorrectly released slot. This violates the required pool consistency and stale-attribution guarantees.
Required repair: enforce one live acquisition/binding per session ID (coalesce concurrent acquires or reject duplicates), and add IPC single-flight protection for ensureOpenSession. Add a deterministic two-concurrent-acquire regression asserting one owner, consistent activeCount/get/snapshot, one event path, and safe release.

2. BLOCKING — session-creation failure cleanup is not lease-safe and can destroy a same-ID replacement.
Evidence:
- apps/desktop/electron/main/ipc.ts:1404-1419 performs awaited new_session/get_state work, records createdLease/openSessions, and then registers callbacks.
- apps/desktop/electron/main/ipc.ts:1420-1451 contains further awaits (mkdir, credential lookup, set_api_key) after the entry is published.
- apps/desktop/electron/main/ipc.ts:1453-1457 catches any later failure but unconditionally openSessions.delete(createdSessionId), calls pool.release(createdSessionId) without createdLease, and deletes the chat session record.
Impact: if that binding is released and the same ID is reacquired while creation is awaiting, stale failure cleanup erases the replacement openSessions entry, resets/releases the replacement runtime, and deletes its session record. The success path at 1452 can likewise return a stale entry without a final ownership check.
Required repair: capture the exact entry/client/session/lease; revalidate after every await and before every side effect; in catch, release only with createdLease and delete openSessions only when openSessions.get(id) === entry. Do not delete a replacement session record. Validate ownership again before returning success. Add a deferred set_api_key/mkdir failure regression with same-ID release/reacquire.

3. BLOCKING — logger replacement marker can preserve a registered secret.
Evidence:
- apps/desktop/electron/main/logger.ts:14-21 replaces every registered value with the fixed string '[已删除]'.
- apps/desktop/electron/main/logger.ts:110-112 accepts any nonempty text as a redaction value.
- apps/desktop/electron/main/logger.ts:32-34 uses the same marker in malformed-line placeholders; 146-147 applies redactText to future writes; 152-156 applies it to exports.
Impact: registering '已删除' produces '[已删除]', which still contains the exact secret; registering '[已删除]' leaves it unchanged. Thus valid history rewrites, malformed placeholders, future appends, console output, and exports can all preserve a registered secret, contrary to the no-preserved-secrets requirement.
Required repair: use a redaction marker guaranteed not to contain any registered secret (or remove the value), and verify the final serialized output against the complete redaction corpus. Add regressions for '已删除' and '[已删除]' across rewrite, malformed history, future append, and export.
