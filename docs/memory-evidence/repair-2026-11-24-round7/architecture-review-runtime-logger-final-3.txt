Remaining blocking findings

1. BLOCKING — logger replacement can recreate a registered secret across the marker boundary.
Evidence: apps/desktop/electron/main/logger.ts:14-18 and apps/desktop/electron/main/logger.ts:27-44, with the concrete x"[已删除] example above.
Impact: valid-history rewrite, direct export, future append and console output can still contain the registered secret in raw or JSON-escaped form. This violates the no-preserved-secrets requirement even though the two original marker literals are handled.
Required repair: use a marker whose scalar characters are absent from the complete registered corpus for all cases (the existing Unicode-scalar fallback has this property), or iterate to a verified fixed point with cycle handling. Verify the final serialized output against every raw and JSON-escaped secret before rewrite/write/export/console output. Add regressions for prefix/suffix-wrapped markers containing quotes, backslashes and control characters.

2. BLOCKING — sparkii:promptSession does not validate the captured binding lease across awaits, allowing an old prompt to affect a same-ID replacement.
Evidence:
- packages/agent-host/src/pi-runtime-pool.ts:244-257 exposes one stable facade per slot; packages/agent-host/src/pi-runtime-pool.ts:222-241 has no lease/ownership gate for ordinary commands. Reusing the slot intentionally returns the same client with a rotated lease, as asserted at packages/agent-host/test/pi-runtime-pool.test.ts:725-739.
- apps/desktop/electron/main/ipc.ts:1367-1385 captures OpenSession, then awaits settings/model/key/thinking-level work and returns without comparing open.lease to rt.pool.getBinding(sessionId). selectModel re-resolves the current pool client at apps/desktop/electron/main/workflow.ts:169-203, so it can configure the replacement even when the old client differs.
- apps/desktop/electron/main/ipc.ts:1714-1797 carries that OpenSession through attachment staging, image reads, get_state, task start, prompt/steer/follow_up and the final get_state without any client/session/lease validation.
Impact: if the slot is released and the same ID is reacquired while promptSession is awaiting, the stale handler can change the replacement model/thinking level, send the old prompt/steer/follow_up into the replacement when the facade is reused, arm/update replacement bookkeeping, and return success. This is the same-ID binding corruption the lease mechanism is intended to prevent.
Required repair: capture the immutable binding at promptSession entry and validate pool membership, client identity, session ID and lease before subscription/send, on every event, after every await and before success/bookkeeping. Abort stale work without touching the replacement and pass the captured lease to any cleanup/release. Add a deferred attachment or model/key regression that releases and reacquires the same ID on the same client while the old prompt is suspended.
