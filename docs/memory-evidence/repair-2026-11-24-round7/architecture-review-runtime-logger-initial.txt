## Review findings

1. **Blocking — stale events can be attributed to the next session after reset succeeds.**
   - `release()` clears ownership only while `resetting` is true, then assigns the slot to the next session: `packages/agent-host/src/pi-runtime-pool.ts:310-324,347-349`.
   - Event handling has no session generation or reset-boundary guard; any subsequent event updates whichever session currently owns the slot: `packages/agent-host/src/pi-runtime-pool.ts:187,240-250`.
   - Consumers likewise read the current live session ID when forwarding events, so an old-session event arriving after rebind is delivered as the new session: `apps/desktop/electron/main/ipc.ts:869-874`.
   - The regression test emits an event only during reset and asserts attribution is null; it never emits an old-session event after reset completion and rebind: `packages/agent-host/test/pi-runtime-pool.test.ts:169-201`.
   - Required repair: introduce an event generation/reset barrier that rejects pre-reset events after rebind, and add a regression covering an old event after successful reset plus a legitimate event from the new session.

- Logger redaction recursively transforms string values while preserving keys; nonempty rewrites receive one trailing newline; future appends and exports use the same structured redaction path.
