# Sparkii Desktop 智能体路线图

**状态：** 讨论稿（待评审后生效）
**日期：** 2026-09-22
**适用产品：** Sparkii Desktop（本地部署、可审计的多智能体工作台）

---

## 1. 本文的定位

本文回答一个问题：**在现有平台能力之上，下一个智能体做哪一个，后续按什么顺序推进。**

它只描述能力边界、依赖关系、排序理由与阶段目标，不含商务信息与具体现场信息。每个阶段真正落地时，另出设计规格与实现计划（`docs/superpowers/specs/`、`docs/superpowers/plans/`），本文不替代它们。

本文的排序结论基于两类事实：**仓库中已实现的平台能力**（可核对到文件）与**各业务方向对数据、界面的真实依赖**。

## 2. 平台能力现状

### 2.1 已具备的能力

| 能力 | 说明 | 载体 |
| --- | --- | --- |
| 内嵌 Agent 运行时 | Agent 内核随应用内嵌，无需外部运行时；有上限的进程池，每会话独立 | `packages/agent-host` |
| 智能体配置包 | 页面、流程、技能、主题、权限、模型路由全部声明式；签名完整性校验 | `packages/config`、`apps/desktop/agents/*` |

| 知识检索 | 本地语料 BM25、SparkiiRAG（混合检索）、SparkiiOnto（本体产品的兼容检索面）三选一，按配置包的后端判别 | `packages/connectors/src/*` |

| 确定性审核引擎范式 | 解析 → 对齐 → 规则 → 发现 → 人工复核 → 导出，规则可配置 | `apps/desktop/agents/procurement-review/engine` |
| 智能体可用工具 | `document.read`、`knowledge.search`、`knowledge.fetch_document`、`report.export` | `apps/desktop/electron/main/connector-registry.ts` |

### 2.2 尚未具备的能力（决定排序的五个缺口）

这五项不是"某个智能体的功能"，而是**平台级缺口**。在补齐之前，相关方向只能以"人工上传导出文件"的降级形态交付。

| 缺口 | 现状 | 影响的方向 |
| --- | --- | --- |
| **本体（图谱）工具面** | 只接通了本体产品的兼容检索面（探活、能力协商、列知识域、词法检索、打开原文）。同进程已挂载的图检索、路径、因果链、决策链、血缘、SPARQL 等端点**尚未接通** | 工艺诊断、环保根因、进场质量预警 |
| **外部业务数据接入** | 除知识服务外，没有任何业务系统连接器；只有本地文件与知识服务两类数据入口 | 销售预警、环保预警、生产报表、统一查询、采购价格趋势 |
| **值守能力** | 没有定时任务、没有预警推送通道、没有报警面板（`dashboard` 表面仅在 schema 中声明，未实现） | 所有"预警 / 推送 / 日报"类方向 |
| **结构化业务数据** | 仓库内只有会话、审计、错误三类 SQLite 存储；没有业务记录存储与表单配置能力 | 化验数据线上化、单据审核、日报沉淀 |
| **表格类报表导出** | 只有 DOCX，没有 XLSX 与固定模板报表 | 生产日报、经营报表、三岗聚合报表 |

## 3. 候选方向与差距评估

就绪度 = 现有平台能力覆盖程度 × 数据可得性 × 交付风险可控性。

| 方向 | 目标用户 | 现有能力可用部分 | 主要缺口 | 就绪度 |
| --- | --- | --- | --- | --- |
| **生产工艺诊断** | 生产 | 规则引擎范式、知识检索、报告导出、审批审计 | 本体工具面、工况数据入口、图谱内容建模 | 中 |
| **质控化验线上化 + 质量预警** | 质控 | 文档解析（照片 / 扫描件）、报告导出 | 手写识别精度、结构化存储与表单、XLSX 报表 | 中 |
| **采购市场预判** | 采购 | 需求计划审核部分已在采购审核中实现 | 价格时序数据、外部行情（内网隔离）、推送 | 中偏低 |
| **销售分析与预警** | 销售 | 报告生成 | 发运数据接入、定时值守、推送 | 低 |
| **生产报表与预测** | 生产管理 | 报告生成、规则引擎 | 多源数据接入、XLSX 模板、定时 | 低 |
| **环保分析与预警** | 环保安全 | 与工艺诊断共用图谱与规则 | 监测数据接入、值守、推送 | 低 |
| **企管员工服务与合规** | 企管 | 知识问答已具备同等能力 | 制度语料、人事数据、合规规则 | 高（可快赢） |
| **行政统一查询** | 行政 | 知识问答的检索链路 | 单点登录、全系统数据接口 | 低 |

## 4. 排序原则

1. **价值密度优先。** 同等投入下，优先做能直接影响成本或风险、且效果可度量的方向。
2. **平台复用优先。** 优先复用已有确定性引擎范式（解析 → 规则 → 发现 → 复核 → 导出）与已有知识、文档、报表能力。
3. **数据可得性优先。** 不把"等待外部系统开放接口"作为首个交付的硬前置；接口未通时用人工上传导出文件的降级形态先跑通价值。
4. **一次建设、多方受益。** 优先做能沉淀为平台能力或公共数据资产的方向，后续方向可复用。
5. **质量承诺要诚实。** 不承诺当前技术条件下不可靠的能力（例如手写识别准确率、精确数值预测）。

## 5. 路线图

### 阶段 0 · 平台前置（不新增智能体）

本阶段不产出面向业务人员的智能体，但它是阶段 1 的关键路径。

**0.1 本体因果链工具面（最小集）**

- 目标：让智能体能沿因果链推理，而不是只做文档片段检索。
- 范围：接通本体产品的图能力最小集——给定一个异常指标/节点，取上下游节点、关联参数、路径与因果距离；返回结构可被规则与模型共同消费。
- 非目标：SPARQL 全量暴露、写图、本体版本管理与评审流程。
- 依赖：本体产品的兼容检索链路已接通（已完成）；本体侧需存在真实工艺图谱数据。
- 完成判据：契约测试覆盖各端点的成功与失败语义；一次"异常指标 → 上游可疑节点列表"的真实调用可跑通。

**0.2 本体会话级接通**

- 目标：让配置为本体后端的智能体在界面上完整可用（选域、出处、点出处打开原文）。
- 范围：选域控件按后端取列表；出处带后端归属；历史会话读回语义不变。
- 非目标：改动任何既有智能体的默认后端或行为。
- 完成判据：一个配置为本体后端的会话能完成"选域 → 提问 → 出处 → 打开原文"的完整闭环。

**0.3 本地模型端点与离线交付验证**

- 目标：满足"数据不出本机/本厂"这一产品红线。
- 范围：以内网自建推理服务（OpenAI 兼容端点）作为自定义服务商接入，完成端到端验证；给出离线交付检查清单。
- 非目标：随安装包分发模型权重（按需评估）。
- 完成判据：断开公网后，对话、流程、审批、导出全链路可用。

**0.4 结构化业务数据与表格报表（可与阶段 1 并行）**

- 目标：为"记录型"业务（化验数据、单据、日报）提供落点。
- 范围：可配置业务表单、结构化记录存储、XLSX 导出。
- 非目标：通用低代码平台、跨记录复杂计算。

### 阶段 1 · 生产工艺诊断智能体 v1

- **目标：** 把工艺异常的发现与定位从"依赖人工经验、滞后一小时"变成"系统先给结论、人再确认"。
- **范围：** 工况快照入口（录入 / 上传 / 表单，先不接实时系统）→ 多指标阈值规则筛查 → 沿因果链定位根因 → 给出调整方向建议 → 生成诊断报告（审批后导出）→ 诊断记录沉淀为可检索知识。
- **明确不做：** 实时数据接入、秒级告警、自动下发调整、外部系统推送。
- **依赖：** 阶段 0.1（本体工具面）、阶段 0.3（离线模型）；业务侧需完成核心工艺节点的图谱建模。
- **完成判据：** 给定一份工况快照，系统能给出根因结论、可解释的推理路径与调整方向，全过程留痕；报告可导出、可回溯到审计。

### 阶段 2 · 质控化验数据线上化 + 质量预警

- **目标：** 把线下的化验数据变成可查询、可分析、可追溯的数据资产，并在此基础上做质量预警。
- **范围：** 指标可配置表单 → 录入（认字能力作预填，保留人工复核）→ 多岗位数据聚合报表 → 质量日报摘要 → （依赖图谱）进场质量预警。
- **明确不做：** 承诺手写识别准确率；替代人工复核。
- **依赖：** 阶段 0.4（结构化存储与表格报表）；预警部分依赖阶段 0.1 与阶段 3 的推送能力。
- **完成判据：** 一个完整周期的数据可录入、可聚合、可导出；日报摘要可读且每条结论可追溯到数据。

### 阶段 3 · 外部数据接入与值守能力（平台级）

- **目标：** 让智能体从"人点开才跑"升级为"到点自己跑、有异常主动提醒"。
- **范围：** 业务系统只读接入（按现场可开放顺序推进）→ 定时任务 → 预警推送 → 报警/监控面板表面。
- **明确不做：** 向业务系统写入、自动处置。
- **依赖：** 现场系统接口与只读权限；接口未开放期间，用"上传导出文件 + 定时批处理"作为过渡形态。
- **完成判据：** 至少一个方向能无人值守地按周期运行，并把异常推送到人。

### 阶段 4 · 数据依赖型方向（按此顺序）

| 顺序 | 方向 | 先做什么 | 后做什么 |
| --- | --- | --- | --- |
| 4.1 | 生产报表与预测 | 生产日报自动生成 | 经营报表合成、发电量类预测集成 |
| 4.2 | 销售分析与预警 | 客户流失预警、区域异常识别 | 价格—销量关联分析 |
| 4.3 | 采购市场预判 | 内部价格趋势研判、需求计划审核建议 | 外部行情与政策推送 |
| 4.4 | 环保分析与预警 | 超标根因分析（复用工艺图谱） | 工艺—环保联动预警 |
| 4.5 | 行政统一查询 | 统一自然语言查询入口 | 单点登录打通 |

排序理由：4.1 与 4.2 的产出最容易被现场直接验收；4.3 的需求计划部分已在采购审核中实现，增量集中在外部分数据源；4.4 与阶段 1 共用图谱与规则，边际成本最低；4.5 依赖面最广，放在最后。

### 贯穿全程：快赢与补口项

以下工作成本可控，可在任意空档插入，用来保持交付节奏：

- **企管员工服务与合规**：企业知识问答能力已具备，主要是制度语料整理、场景化封装与合规检查技能。
- **合同审核补口**：关键时间节点自动提取（结构化输出）。
- **采购审核补口**：单据一致性审核；供应商质量风险定位（依赖阶段 2 的数据）。

## 6. 风险与前置假设

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 现场系统接口开放滞后 | 预警与报表类方向无法按期交付 | 阶段 3 之前一律采用"上传导出文件"的降级形态；接口开放作为并行的独立工作项推进 |
| 工艺图谱内容未建模 | 因果链推理无数据可依 | 图谱建模作为业务侧前置任务显式列入计划，先粗粒度（核心节点）再细化 |
| 机器视觉类识别精度 | 手写数据录入不可靠 | 认字能力只作预填，人工复核兜底；对外不承诺准确率 |
| 图谱/检索质量与预期不符 | 问答体验落差 | 按后端显式标注能力差异，场景与查询方式匹配（引用式查询 vs 自然语言长问句） |
| 离线推理算力不足 | 本地模型响应慢 | 按任务分级路由：轻任务用小模型，重任务用大模型；非实时任务异步处理 |

## 7. 待决策项

1. 工艺诊断 v1 是否接受"工况快照（录入/上传）"形态，而不等待实时数据接入。
2. 手写化验数据的对外能力口径：是否统一为"识别预填 + 人工复核"。
3. 本地模型的交付形态：内网自建推理服务接入，还是随包分发权重。
4. 阶段 0.4（结构化业务数据）与阶段 1 的先后或并行关系。
5. 本体侧图谱建模的负责人、范围与验收方式。
