# 任务边界驱动的智能体审批与安全执行设计

- 日期：2026-10-21
- 状态：设计已确认；第 1–3 轮架构审核通过；可进入实现设计
- 适用范围：Sparkii Desktop 通用智能体，以及后续沿用统一执行平面的业务智能体
- 平台范围：Windows 当前优先；macOS 与 Debian/Ubuntu Linux 为后续目标平台

## 1. 摘要

当前审批机制把大量普通工作区操作当成高风险动作，导致读取辅助命令、文件修改和多文件任务频繁打断用户。新的设计把授权单位从“每次工具调用”调整为“一个用户任务及其工作区”：

> 任务工作区内的普通读写、创建、修改、移动、重命名、删除、测试、构建和本地命令由智能体自主完成；只有越出任务边界、访问外部系统、产生外部副作用、触碰信任锚或命中不可覆盖的灾难目标时，才进入人工审批或直接拒绝。

本设计不把模型行为是否“可靠”当作安全前提。模型、工具参数、工作区内容、技能和子 Agent 都按不可信输入处理。安全来自确定性的能力边界、工作区沙箱、外部能力网关和审计，而不是来自提示词约束或模型自述。

恢复能力是用户体验增强项，不是工作区操作的授权前置条件。普通工作区操作在快照不可用时仍然可以执行；系统通过任务变更摘要、版本控制、可选回收区和可选检查点降低恢复成本。

## 2. 目标与非目标

### 2.1 目标

1. 默认允许智能体完成工作区内的完整任务，不为普通文件操作增加逐次确认。
2. 让安全边界可证明、可测试、可跨平台复用，不依赖每个命令前缀的无限扩张。
3. 将外部网络、企业系统和跨边界文件访问纳入明确的能力授权。
4. 保留高风险动作的失败关闭、二次确认和不可覆盖拒绝。
5. 让所有自动执行、审批、拒绝和能力扩张都有审计记录。
6. 支持后续增加 macOS、Debian/Ubuntu、新工具、新连接器和新业务 Profile。

### 2.2 非目标

1. 本文不定具体代码结构、数据库字段或实施顺序；实施设计另行编写。
2. 本文不改变业务 Workflow 中的人工复核语义。合同复核、采购复核等业务确认与安全审批是两条独立流程。
3. 本文不承诺工作区内所有操作都可恢复，也不把长期备份、版本控制或企业数据留存纳入本系统。
4. 本文不提供“全部允许”运行模式。无人值守任务遇到需要人工的请求时应拒绝或暂停，不能无限等待。
5. 本文不要求所有平台使用完全相同的系统调用，只要求满足同一组安全不变量。

## 3. 设计原则

### 3.1 一个授权单位：任务工作区

用户选择一个工作区并提交任务后，该工作区成为本任务的可写范围。智能体不需要证明每个文件都属于任务；文件是否合理属于任务质量问题，通过任务结束后的变更摘要和 diff 复核，而不是通过逐文件权限判断。

### 3.2 一个审批触发点：能力边界

审批只用于授予任务当前不具备的能力，例如：

- 读取工作区外目录；
- 访问网络；
- 调用外部业务系统；
- 修改凭据或控制平面配置。

审批不是普通文件操作的成功步骤。

### 3.3 一个不可覆盖的安全底线

能力授权、会话规则和自动评审都不能覆盖灾难目标保护。文件系统根目录、用户主目录、系统目录、Sparkii 数据目录和整个任务工作区根目录不得由智能体自动删除或整体覆盖。

### 3.4 模型不可信，影响范围可控

系统不得依赖以下假设：

- 模型不会主动删除重要文件；
- 模型能准确判断自己的操作是否危险；
- 模型生成的脚本与命令解释一致；
- 工作区内容、技能或配置文件不含提示注入；
- 子 Agent 会遵守父 Agent 的文本说明。

系统通过进程隔离、路径边界、网络边界、确定性策略和外部能力网关限制结果。

### 3.5 执行后复核优先于执行前打断

对于可限定在工作区内的任务，用户主要在执行后查看变更、测试结果和删除清单。只有系统无法安全容纳影响范围，或副作用已经离开本机工作区时，才要求事前确认。

## 4. 安全模型

### 4.1 信任边界

| 对象 | 信任级别 | 说明 |
| --- | --- | --- |
| Main 控制平面 | 可信 | 持有策略、审批状态、审计、凭据和确定性执行器 |
| Renderer/UI | 受限可信 | 可发起和展示请求，不能直接获得系统能力或密钥 |
| Pi/Agent Runtime | 不可信执行者 | 只生成动作请求，不能自行授权或扩大能力 |
| 模型输出 | 不可信 | 只能形成动作请求，不能形成授权决定 |
| 工作区内容与脚本 | 不可信 | 可能包含提示注入、恶意依赖或破坏性脚本 |
| 子 Agent | 不可信执行者 | 只能继承或收窄父任务权限 |
| 外部连接器 | 受控能力 | 必须经过 Main 侧能力网关和冻结参数执行 |

### 4.2 威胁模型

设计必须抵御或限制以下风险：

1. 通过 `..`、符号链接、目录联接、挂载点或重解析点逃出工作区。
2. 通过 Shell 子进程、脚本解释器、包管理器和构建工具绕过应用层路径检查。
3. 通过继承环境变量、读取主目录配置或连接本机服务获取凭据。
4. 通过提示注入让 Agent 把工作区内容解释为扩大权限的指令。
5. 并发 Agent 或外部编辑器同时修改同一路径，导致回滚或审计失真。
6. 构造一个“批准时”和“执行时”参数不同的动作，绕过冻结参数。
7. 利用宽松网络白名单、域名前置或本地回环服务进行数据外传。
8. 让 Agent 修改权限策略、沙箱配置或可执行钩子，从而为后续动作提权。
9. 通过灾难路径删除工作区根目录、用户目录、系统目录或 Sparkii 控制数据。

### 4.3 边界定义

一个任务授权域至少包含：

- 一个可写工作区根；
- 一个与工作区分离的任务私有 scratch；
- 零个或多个只读输入目录或文件；
- 允许调用的工具与连接器能力；
- 允许访问的网络域；
- 允许执行的运行模式；
- 授权发起人、Profile 和任务标识；
- 授权有效期。

Agent 只能读取这些字段，不能修改。需要新增能力时，只能向控制平面提交 `CapabilityRequest`。

#### 4.3.1 Workspace Admission

Workspace 在创建 Task Grant 前必须通过确定性的准入检查。准入检查由 Platform Adapter 解析真实文件系统对象，不使用纯字符串前缀判断。

准入规则：

1. 文件系统根、用户主目录和驱动器根不能作为 Workspace 根对象，但其普通项目后代可以按规则成为 Workspace。
2. 操作系统目录、平台程序目录、Sparkii 数据、审计、权限、运行态、凭据和沙箱控制目录不能作为 Workspace，其**任意后代也不能**成为 Workspace。
3. Workspace 不得包含 Sparkii 控制数据或其他受保护根。
4. Workspace 位于用户主目录或普通盘符下时，Workspace 自身及其完整祖先链不得落入平台定义的受保护子树，例如系统目录、程序目录、凭据目录、应用数据目录和 Sparkii 控制目录。
5. 用户主目录下的普通项目目录可以成为 Workspace；拒绝的是主目录本身、受保护子树及其后代，不是所有用户主目录后代。
6. Workspace 内通过注册表识别出的受保护子树不因 Workspace 准入通过而获得普通 CRUD 权限。
7. 对尚不存在的 Workspace，校验最近的已存在祖先并固定预期的创建身份；创建完成后重新执行准入检查。
8. 切换 Workspace、恢复会话或从历史引用恢复时，必须重新执行准入，不能信任数据库中的旧路径。
9. Workspace 变更后，旧 Task Grant 立即失效，并终止旧 Workspace 中仍在运行的 Action。

平台适配器必须能识别同一文件对象的别名，包括盘符与扩展路径前缀、UNC、卷 GUID、挂载点、符号链接、目录联接、硬链接和重解析点。任一别名映射到受保护目标时，准入失败关闭。

受保护根按允许后代策略分为两类：

| 类别 | 对象 | 后代策略 |
| --- | --- | --- |
| 边界根 | 文件系统根、用户主目录、驱动器根 | 根对象本身禁止作为 Workspace；普通后代可成为 Workspace，但受保护子树除外 |
| 闭包根 | 操作系统目录、平台程序目录、Sparkii 控制目录、凭据目录、任务控制与运行态目录 | 根对象及其任意后代均禁止作为 Workspace |

Platform Adapter 必须返回闭包根的规范化对象身份，并对 Workspace 的完整祖先链执行包含判断。目录联接、符号链接、挂载点或重解析点映射到闭包根后代时，按真实目标拒绝。

#### 4.3.2 Action 权威

Agent Runtime 提交的是原始工具意图，不是已经成立的安全事实。

Main 必须依据可信工具注册表、参数 Schema、Task 上下文和 Platform Adapter 重新生成：

- 实际 Capability；
- 规范化目标；
- 风险等级；
- 外部副作用类型；
- 冻结参数；
- 面向用户的影响摘要和预览。

Runtime 提供的 `toolName`、`risk`、`summary`、目标路径和副作用描述只能作为未验证提示。任何展示给用户的审批内容都必须来自 Main 的重新计算结果。

在审批时和最终执行时都要重新校验目标对象、父链和参数哈希。目标身份、父目录或对象类型发生变化时，原审批失效并拒绝执行。

## 5. 核心概念

### 5.1 Task

Task 是用户一次可识别的工作目标。一个 Task 可以包含多个 Agent 轮次、工具调用、子 Agent 和 Workflow 步骤。Task 的授权不因模型内部计划变化而失效，但会在用户结束任务、会话关闭、超时或权限被撤销时失效。

Task 进入终止状态时：

- 立即停止生成新的 Action；
- 终止仍在运行的进程树；
- 关闭任务专属网络连接和 Capability Gateway 租约；
- 拒绝排队的越界动作；
- 记录实际终止结果和外部副作用确认状态。

本地终止不等于外部系统写入失败。外部副作用必须通过查询、幂等键或补偿流程确认最终结果。

### 5.2 Workspace

Workspace 是用户授予 Agent 的普通文件可写边界。Workspace 内普通内容不按文件类型、扩展名、操作次数或创建/修改/删除动作逐项审批。

### 5.3 Input Resource

Input Resource 是任务需要的只读资料，例如合同原文、需求文档、知识库文档或用户额外指定的目录。默认不可修改。

### 5.4 Capability

Capability 是对外影响的类型化描述，例如：

- `fs.read`；
- `fs.write`；
- `process.exec`；
- `net.connect`；
- `connector.invoke`；
- `task.delegate`。

工具负责声明自己需要的 Capability 和参数影响范围，不负责自行决定是否已获批准。

### 5.5 Task Grant

Task Grant 是控制平面依据用户任务、Profile、运行模式和平台安全能力生成的授权集合。

Standard 模式的默认 Task Grant 包含：

- 工作区普通文件读写与删除；
- 与工作区分离、仅当前 Task 可访问的私有 scratch；
- 工作区内进程执行；
- 工作区内的测试、构建、格式化和本地 Git 操作；
- 已显式绑定的只读输入；
- 无网络、无外部写、无工作区外访问。

### 5.6 Action

Action 是 Main 根据 Agent 原始工具意图生成的结构化动作请求，至少包含：

- 工具标识和能力类型；
- 规范化参数；
- 目标路径或资源；
- 预期副作用摘要；
- 是否改变信任锚；
- 请求所属 Task、Session 和 Call。

影响字段由 Main 计算，不由 Runtime 自行声明。

### 5.7 External Effect

External Effect 是离开任务工作区后不可由工作区隔离直接消除的影响，包括：

- 网络上传或下载；
- 企业系统写入；
- 消息、邮件、审批、工单和部署；
- 推送远端仓库；
- 修改工作区之外的用户文件。

External Effect 必须经能力网关，不能由 Agent 子进程直接完成。

## 6. 运行模式

### 6.1 计划模式

- 可读取任务工作区和已绑定输入；
- 可进行搜索和分析；
- 不得修改工作区；
- 不得访问未授权网络或外部系统；
- 可以向用户提交计划。

### 6.2 标准模式

标准模式是默认模式。

- 工作区内普通文件 CRUD 自动执行；
- 工作区内进程在沙箱内自动执行；
- 临时文件写入任务私有 scratch，不视为越界；
- 测试、构建、lint、格式化和本地 Git 操作自动执行；
- 越界读取、联网和外部写进入能力审批；
- 灾难目标和信任锚仍受不可覆盖保护。

可复用的语言工具缓存和包管理器缓存必须使用受控任务缓存或预配置的共享只读缓存。默认不向 Agent 开放用户任意缓存目录；如果共享缓存需要写入，必须按平台策略隔离并清理。

### 6.3 严格模式

严格模式供高敏感客户或首次接入使用。

- 工作区内写操作和进程执行按 Profile 策略审批；
- 只读操作仍可直接执行；
- 越界和外部能力继续审批；
- 灾难目标和信任锚保护不变。

严格模式是可选保护，不是默认体验。

### 6.4 无人值守语义

无人值守不是独立用户模式，而是 Task 的执行属性。处于无人值守状态时：

- 已有授权范围内的工作区操作继续执行；
- 遇到需要人工的 `ASK` 决策时立即拒绝或暂停任务；
- 不得升级成自动通过；
- 不得通过重复重试绕过拒绝。

## 7. 决策模型

控制平面按固定顺序计算：

```text
规范化 Action
  → 灾难目标与硬拒绝检查
  → 平台安全能力检查
  → Task Grant 能力匹配
  → Profile 策略覆盖
  → 输出 ALLOW / ASK / DENY
```

判定优先级为：

```text
硬拒绝 > 人工明确拒绝 > 严格策略 > Task Grant > 默认拒绝
```

### 7.1 三类结果

| 结果 | 含义 | 用户体验 |
| --- | --- | --- |
| `ALLOW` | 能力已在 Task Grant 内且安全边界可执行 | 不弹窗，记录审计并实时展示动作状态 |
| `ASK` | 需要新增能力或进入人工业务确认 | 展示能力增量、目标和影响；由人决定 |
| `DENY` | 未授权、不可覆盖拒绝或平台无法提供安全执行 | 不执行，返回可理解的拒绝原因 |

### 7.2 标准模式决策表

| Action | 结果 |
| --- | --- |
| 工作区内读取、搜索 | `ALLOW` |
| 工作区内创建、修改、移动、重命名文件 | `ALLOW` |
| 工作区内删除普通文件或普通子目录 | `ALLOW` |
| 写任务私有 scratch 或受控任务缓存 | `ALLOW` |
| 工作区内测试、构建、lint、格式化 | `ALLOW` |
| 工作区内本地 Git 修改、暂存、提交 | `ALLOW` |
| 读取工作区外普通文件 | `ASK` 或 `DENY` |
| 访问未绑定网络 | `ASK` 或 `DENY` |
| 外部系统写入 | `ASK`，业务 Profile 可要求更高权限 |
| 修改凭据、权限规则、Sandbox 配置 | `DENY` 或受控管理员流程 |
| 删除整个 Workspace 根 | `DENY` |
| 删除文件系统根、用户主目录、系统目录、Sparkii 数据目录 | `DENY` |
| 平台无法建立所需沙箱 | 降级为 `DENY` 或严格模式，不得静默放行 |

### 7.3 不按操作次数审批

以下因素不得单独触发审批：

- 单轮修改文件数量；
- 新增或删除目录深度；
- 使用 `edit`、`write`、`bash` 还是别的工具；
- 使用 Shell、脚本解释器、构建工具或包管理器；
- 删除是否可由应用层快照恢复。

这些因素可以影响风险提示、审计详情或任务后的变更摘要，但不能替代工作区边界作为授权依据。

## 8. 目标架构

```text
┌────────────────────────────────────────────────────────────┐
│ Renderer                                                   │
│ 任务输入 · 权限状态 · 工具时间线 · 例外审批 · 变更复核      │
└──────────────────────────┬─────────────────────────────────┘
                           │ typed IPC
┌──────────────────────────▼─────────────────────────────────┐
│ Main 控制平面                                               │
│ Task Grant · Policy Engine · Approval Orchestrator          │
│ Capability Gateway · Audit · Recovery Coordinator           │
└───────────────┬───────────────────────────┬─────────────────┘
                │                           │
┌───────────────▼──────────────┐  ┌─────────▼────────────────┐
│ Agent Runtime / Pi           │  │ External Connectors      │
│ 只提交 Action，无授权能力     │  │ 企业系统 · 消息 · 导出    │
└───────────────┬──────────────┘  └─────────┬────────────────┘
                │                           │
┌───────────────▼───────────────────────────▼────────────────┐
│ Execution Plane                                             │
│ Workspace Sandbox Adapter · Process Supervisor              │
│ Frozen Payload Executor · Platform Capability Adapter       │
└─────────────────────────────────────────────────────────────┘
```

### 8.1 Policy Engine

职责：

- 从可信工具定义重新计算 Agent 原始意图的实际能力与影响；
- 验证 Action 是否属于 Task；
- 规范化路径、资源、网络和外部目标；
- 匹配 Task Grant 与 Profile 策略；
- 执行硬拒绝和灾难目标检查；
- 输出确定性的 `ALLOW / ASK / DENY`。

Policy Engine 不解释模型自然语言，不从审批摘要推断授权。

### 8.2 Approval Orchestrator

职责：

- 仅为 `ASK` 创建审批请求；
- 冻结由 Main 重新计算的目标身份、参数和载荷哈希；
- 提供“本次”与“本任务”两种交互授权；
- 管理撤销、过期、在途终止和无人值守拒绝；
- 将决定反馈给控制平面。

持久规则只能在设置或管理员策略中维护，不能从普通运行审批直接获得“永久全权限”。

### 8.3 Capability Gateway

所有外部副作用都必须经过 Capability Gateway：

- 企业系统；
- Git 推送；
- 网络代理；
- 邮件与消息；
- 文件导出；
- 第三方 MCP 或连接器。

Gateway 只执行已批准且未变化的能力请求。参数哈希、目标或副作用描述变化时，原批准失效。

### 8.4 Workspace Sandbox Adapter

每个平台提供统一适配接口，负责：

- 启动受限进程；
- 限定文件系统可写根；
- 限定只读输入；
- 提供任务私有 scratch；
- 阻断默认网络；
- 阻断未授权的系统 IPC、命名管道、本机服务和非任务进程；
- 清理敏感环境变量；
- 终止整个子进程树；
- 提供可执行文件和运行时依赖的最小只读视图；
- 返回目标对象身份和父链校验结果；
- 返回可验证的执行结果。

上层不直接调用平台命令，也不在 Policy Engine 中写 Windows、macOS 或 Linux 分支。

### 8.5 Recovery Coordinator

职责是提供可选恢复，不参与授权：

- 获取 Git diff 和工作区状态；
- 准确记录经过结构化文件工具的变更；对无法观测的 Shell 内部临时写入标注“尽力而为”；
- 提供任务回收区；
- 在用户启用时管理任务检查点；
- 在恢复前检测外部修改和冲突。

Recovery Coordinator 不可用时，普通工作区操作仍然按 Task Grant 执行；系统只降低“一键恢复”能力，不降级为逐动作审批。

## 9. 执行数据流

### 9.1 工作区文件操作

```text
Agent 提交 fs.write/delete Action
  → 规范化并校验目标在 Workspace 内
  → 检查灾难目标和信任锚
  → Task Grant 命中
  → ALLOW
  → 在沙箱内按已校验对象身份执行
  → 写入 Tool 时间线和审计
  → 任务结束后汇总变更
```

整个过程不创建 Approval Proposal，不弹出审批面板。

### 9.2 工作区命令

```text
Agent 提交 process.exec Action
  → 检查目标工作区与运行模式
  → 启动平台沙箱
  → 映射任务私有 scratch 和受控缓存
  → 注入最小环境变量
  → 默认无网络
  → 默认无宿主 IPC、命名管道、本机服务和窗口自动化
  → 执行并将输出流回会话
  → 记录命令摘要、退出码和影响范围
```

安全由沙箱执行，不允许靠不断扩充“安全命令前缀”实现。

### 9.3 越界或联网请求

```text
Action 需要未授权 Capability
  → Policy Engine 返回 ASK
  → Approval Orchestrator 冻结请求
  → UI 展示能力增量、目标、影响和预览
  → 用户拒绝 / 仅此次 / 本任务
  → Gateway 或 Sandbox 扩展限定能力
  → 执行并审计
```

用户批准的是能力与冻结参数，不是对任意后续动作的概括授权。

### 9.4 用户主动触发的动作

用户在系统对话框中明确选择文件、目标目录或点击“导出”“发送”等动作时，该动作本身构成对完全相同目标和载荷的授权。

如果 Agent 在用户操作后改变了目标、接收方、正文或数据范围，原授权失效，必须重新计算策略。

### 9.5 子 Agent

- 子 Agent 继承父 Task Grant；
- 子 Agent 可以进一步收窄权限；
- 子 Agent 不能扩大父 Task Grant；
- 子 Agent 的越界请求必须携带父 Task、发起 Agent、委派范围和冻结目标；
- 用户批准只能扩展明确选择的父 Task 或子 Agent 能力，不能默认扩展到同 Task 下任意同级子 Agent；
- 父 Task 撤销后，所有子 Agent 授权立即失效。

## 10. 能力授权规则

### 10.1 交互授权范围

普通审批只提供：

- **拒绝**；
- **仅此次**：绑定 Main 生成的 Action、规范化目标身份、父链和载荷哈希；
- **本任务**：绑定具体 Capability、目标身份、发起 Agent、委派范围和有效期。

持久授权通过设置页或管理员策略维护，普通审批界面不提供“永久允许任意命令”。

授权撤销会立即停止接受新 Action，并使任务进程、网络连接、Capability Gateway 租约、代理令牌和排队请求进入终止流程。应用崩溃或重启后，旧 Task Grant、审批认领和外部能力租约不得自动恢复，必须按当前 Workspace、模式和 Profile 重新计算。

### 10.2 高风险审批

高风险动作仍使用强制模态和二次确认，但必须避免与普通工作区操作混为一谈。

高风险示例：

- 工作区外大面积写入；
- 生产系统不可逆更新；
- 推送、部署和外部消息群发；
- 修改安全策略或连接器凭据。

灾难目标是不可覆盖拒绝，不进入普通高风险审批。

### 10.3 自动决策可见性

所有 `ALLOW` 决策都应有可解释原因，例如：

- “工作区内文件修改”；
- “任务已获网络访问：registry.npmjs.org”；
- “用户主动选择导出路径”。

自动执行不得变成静默黑箱。

## 11. 工作区与平台安全

### 11.1 路径规范化

所有平台必须：

- 在策略判定前解析绝对路径；
- 处理大小写、分隔符、Unicode、8.3 短名、DOS 设备路径、扩展路径前缀和卷标识差异；
- 拒绝越过工作区的 `..`；
- 解析或拒绝可逃出工作区的符号链接、目录联接、重解析点和挂载点；
- 将工作区根、用户主目录、系统目录和 Sparkii 数据目录作为不可覆盖目标；
- 不因文件不存在而跳过父链安全校验。

路径校验不能采用“先检查字符串、再按字符串重新打开”的模式。批准时记录目标对象身份和父链；执行前重新校验身份。文件修改、删除、移动、重命名和覆盖应尽可能通过平台安全句柄完成，确保检查与使用针对同一对象，防止批准后目标被替换。

### 11.2 进程边界

- 所有工作区命令在受限进程树中执行；
- 子进程必须继承限制；
- 任务取消时终止完整进程树；
- 防止 detached 子进程在任务结束后继续运行；
- 环境变量按白名单注入，不默认继承用户全部环境；
- 工作区内容不能启动未受限的后台常驻进程。
- 默认拒绝访问未授权的命名管道、本机服务、窗口自动化接口、注册表敏感区和非任务进程 IPC；
- 每 Task 提供独立 scratch，scratch 默认不可被其他 Task 读取；
- scratch 和任务缓存受容量、生命周期和清理策略约束；
- 可执行文件、共享库和运行时只开放必要的只读视图，不默认暴露整个用户运行时目录。

仅限制 `cwd`、字符串路径和网络不足以保证进程边界。平台适配器必须同时覆盖文件系统、进程、IPC、系统自动化接口和网络。

### 11.3 网络边界

- 默认无直接网络；
- 网络通过平台代理或受控出站能力；
- 域名授权绑定 Task 和有效期；
- 本机服务和回环地址默认不可访问；
- 不允许通过命名管道、Unix socket、Docker socket、COM、Apple Events 或其他 IPC 绕过网络代理；
- 代理凭据和模型密钥不进入工作区进程环境；
- 无法可靠执行网络隔离时，Standard 模式不得自动开放未授权联网。

### 11.4 外部副作用

- 外部系统调用必须使用 Main 侧凭据；
- Renderer 和 Agent Runtime 不获得长期凭据；
- 外部请求使用冻结参数和幂等键；
- 写入结果以 Main/连接器返回为准；
- 超时不能假定外部写入成功或失败，必须通过查询或幂等接口确认。

## 12. 灾难目标与信任锚

### 12.1 不可覆盖拒绝

以下**目标对象本身**不得由 Agent 删除、重命名、移动、替换或整体覆盖：

- 文件系统根；
- 用户主目录；
- 操作系统目录；
- 驱动器根和顶层系统目录；
- 整个 Workspace 根；
- Workspace 的父目录；
- Sparkii 数据目录、审计目录、权限目录和运行态目录；
- 平台安全适配器使用的控制文件。

这些规则不能被 Task Grant、严格模式例外、自动评审或“本任务允许”覆盖。

保护的是受保护对象和祖先链，不是“保证 Workspace 根下永远有文件”。Agent 可以逐项删除 Workspace 根下的普通子文件和子目录，也可以通过任务脚本删除这些普通子项；系统不承诺阻止用户授权范围内的“内容清空”，只阻止根对象和受保护对象被整体移除或替换。UI 和验收标准必须使用这一准确语义。

### 12.2 信任锚

信任锚是能够让普通文件操作获得额外执行能力或泄露秘密的资源，至少包括：

- 凭据、私钥和敏感 `.env`；
- Agent 权限与审批规则；
- Git hook；
- Shell 启动脚本；
- 可自动执行的全局配置；
- MCP 服务器配置；
- 未受沙箱覆盖的插件或脚本入口。

信任锚保护优先于 Workspace 普通 CRUD 授权。Workspace Admission 通过不等于其中所有子路径都自动成为普通内容。

信任锚由 Main 的可信注册表识别，Profile 可以增加但不能减少平台底线。至少采用以下规则：

1. 凭据、私钥、敏感环境文件以及配置中引用的秘密文件不得进入普通读取、写入或删除能力；
2. `.git` 目录不能整体禁止，因为 Git 命令需要写 index、objects 和 refs，但 `.git/hooks/*`、`core.hooksPath`、filter、fsmonitor、credential helper 等可扩大执行权或泄露凭据的对象和配置受保护；
3. MCP、插件、自动执行脚本、Shell 启动脚本和沙箱外入口按实际对象身份保护；
4. 对信任锚的列举、读取、写入、重命名、删除、复制和 Shell 访问都在 Platform Adapter 与最终执行边界同时失败关闭；
5. 不能只依赖文件名、扩展名或 Pi 工具层过滤；同一对象通过别名、大小写差异、硬链接或重命名到达时仍然受保护；
6. 确有任务需要修改信任锚时，只能进入明确的高风险受控流程，不能被“本任务允许”覆盖；
7. Git 等受信任控制平面操作可以管理必要的仓库元数据，但 Agent 不能借此直接编辑可执行 hook 或安全配置。

## 13. 恢复与任务检查点

### 13.1 与授权解耦

恢复机制不得决定 `ALLOW / ASK / DENY`。不存在“快照失败所以每个操作都审批”的路径。

### 13.2 分层恢复能力

按成本和可用性分层：

1. Git 工作区使用现有 diff、分支和版本历史；
2. 普通文件删除可尽力进入任务回收区；
3. 用户启用的任务检查点保存变化文件版本；
4. 高风险并行任务可选用隔离 worktree；
5. 外部系统副作用依靠幂等、查询和补偿流程，不宣称文件级回滚。

### 13.3 可选检查点

如果启用任务检查点：

- 存储位于 Workspace 之外；
- 按内容哈希去重并压缩；
- 默认排除依赖、构建产物和缓存；
- 受单任务与全局配额约束；
- 任务结束后按保留策略清理；
- 恢复前检测当前内容是否已被用户或其他进程修改；
- 快照存储不能被 Agent 修改。

任务检查点不是长期备份，也不替代 Git 或企业备份。

## 14. 审计与可观测性

审计至少覆盖：

- Task 开始、结束、取消和失败；
- Task Grant 的创建、使用、过期和撤销；
- 每次 `ALLOW / ASK / DENY` 决策及规则原因；
- 审批请求、决定、决定人和意见；
- 外部能力冻结参数哈希；
- 工具执行摘要、退出码和影响范围；
- 平台沙箱启动、降级和失败；
- 恢复操作、冲突和结果。

审计规则：

1. 不依赖模型生成摘要判断事实；
2. 不记录完整密钥、凭据或敏感文件内容；
3. 自动通过也必须有完整记录；
4. 拒绝和超时同样是审计事件；
5. 审计存储对 Agent 只读或不可见；
6. 审计导出保持时间顺序和任务关联。

## 15. 用户界面

### 15.1 标准任务

- 工作区内的文件操作只显示为工具时间线；
- 自动批准不弹窗；
- 工具卡明确显示“工作区内执行”“沙箱内执行”“无网络”等状态；
- 删除文件在任务时间线中显示为删除，不显示为审批；
- 任务结束显示新增、修改、删除和外部影响汇总。

### 15.2 能力审批

审批卡只展示：

- 请求的新能力；
- 规范化目标；
- 为什么会越界；
- 影响预览；
- 拒绝 / 仅此次 / 本任务。

不展示无关的模型自述、工具 UUID 或大段内部 JSON。

### 15.3 权限状态

任务界面应持续显示当前能力，例如：

```text
工作区可写 · 沙箱内命令 · 无网络 · 外部系统未授权
```

用户可以随时撤销本任务能力。

### 15.4 复核与恢复

任务结束后提供：

- 变更文件清单；
- 结构化文件工具产生的准确删除清单；
- 测试和构建结果；
- 外部副作用记录；
- 可用的 diff、恢复和回滚操作。

Shell、构建工具或脚本在内部创建又删除的临时文件可能不留下可观察文件差异。若没有文件系统事件日志，界面必须把这类影响标为“命令级记录、变更清单尽力而为”，不能宣称绝对完整。

恢复能力缺失时必须如实说明，不能用“操作可撤销”掩盖实际情况。

## 16. 跨平台设计

### 16.1 平台无关契约

Platform Adapter 必须提供以下能力：

- 规范化路径并验证 Workspace 边界；
- 启动受限进程；
- 限定文件系统访问；
- 限定网络访问；
- 限定系统 IPC、命名管道、Unix socket、本机服务和宿主自动化接口；
- 清理环境变量；
- 终止进程树；
- 提供任务私有 scratch；
- 提供平台能力自检结果，包括能力清单、沙箱版本、限制项和失败原因。

Policy Engine、Task Grant、审批和审计保持平台无关。

### 16.2 Windows

当前优先平台。适配器需要处理：

- 盘符、UNC 路径和卷 GUID；
- 大小写不敏感路径、8.3 短名、DOS 设备路径和扩展路径前缀；
- 符号链接、目录联接和重解析点；
- 硬链接、挂载点和卷别名；
- Windows Alternate Data Stream；
- 进程树和 Job 生命周期；
- 受限令牌、AppContainer 或其他等效原生隔离能力；
- 注册表敏感区、命名管道、COM/自动化接口、计划任务和非任务进程访问；
- Git Bash、PowerShell 和原生可执行文件的统一边界。

Windows 适配器不能只依赖字符串前缀判断路径，也不能假定 `cwd` 等于安全边界。

Windows 原生沙箱的最小可执行原型必须在实现前完成验证：Workspace 可写、任务 scratch 可写、系统运行时最小只读、默认无网络、无宿主 IPC、完整终止进程树。原型不满足这些条件时，Standard 的进程执行保持失败关闭。

### 16.3 macOS

后续适配器需要处理：

- 大小写敏感和大小写不敏感卷；
- Unicode 文件名校验；
- 扩展属性和文件权限；
- Seatbelt 或其他等效原生沙箱能力；
- 应用授权、辅助功能和 Apple Events 的显式隔离；
- XPC、Mach 服务、Unix socket 和非任务进程访问；
- 任务 scratch、临时目录和系统缓存隔离；
- arm64 与 x86_64 架构。

### 16.4 Debian/Ubuntu Linux

后续适配器优先支持 Debian 和 Ubuntu：

- Bubblewrap、Landlock、seccomp 或其他等效隔离组合；
- User namespace 与 AppArmor 能力检测；
- 网络命名空间或受控代理；
- 挂载点、符号链接和大小写敏感路径；
- Unix socket、抽象 socket、D-Bus、设备和 `/proc` 访问；
- 文件权限、ACL 和可执行位；
- 任务 scratch、临时目录和语言工具缓存隔离；
- 非 root 用户运行；
- 服务器场景可选容器后端。

### 16.5 平台降级

平台无法提供 Workspace 安全隔离时：

- Standard 模式不得自动执行未受限的任意 Shell；
- 可以继续提供只读分析或严格模式；
- 严格模式只能把动作提升为人工审批，不能放宽文件、网络、OS/IPC 和凭据隔离等平台安全绝对不变量；未证明安全的 Shell 仍不可执行；
- UI 必须明确显示安全能力降级原因；
- 不得把“沙箱启动失败”当成“普通审批通过”；
- 安全策略必须失败关闭。

平台能力自检必须区分“可用”“部分可用”和“不可用”。部分可用时只开放被证明安全的能力；不能把整个平台标记为安全后继续执行任意 Shell。

## 17. 可扩展性

### 17.1 新工具

新工具通过 Capability Descriptor 注册：

- 能力类型；
- 目标资源；
- 副作用类型；
- 可预览效果；
- 是否需要外部网关；
- 支持的操作平台。

Capability Descriptor 必须来自 Main 注册的可信代码或受监管包。第三方工具可以声明需求，但 Main 必须验证其实际行为、参数 Schema 和平台副作用，不能让工具通过声明较弱 Capability 绕过策略。核心策略不按工具名称写业务分支。

### 17.2 新连接器

新企业连接器在 Gateway 侧声明：

- 系统标识；
- 读或写能力；
- 允许的资源范围；
- 参数 Schema；
- 幂等能力；
- 审批展示摘要；
- 凭据隔离方式。

Agent 只看到受控能力，不直接持有连接器凭据。连接器能力和审批摘要由 Main 生成，不能直接采用连接器或 Runtime 自报的安全结论。

### 17.3 新 Profile

业务 Profile 可以：

- 选择默认模式；
- 收窄平台允许能力；
- 对特定外部动作增加合规审批；
- 声明只读数据源；
- 提供业务预览和审计元数据。

Profile 不得放宽灾难目标保护、凭据隔离和平台安全底线。

### 17.4 新运行平台

增加平台时只实现新的 Platform Adapter 和一致性测试，不修改 Task Grant、Policy Engine 或审批 UI 语义。

### 17.5 新执行环境

本地进程、远程 Agent、容器和云端沙箱都可以作为 Execution Backend，但必须满足同一接口和安全不变量。

## 18. 与现有系统兼容的约束

1. Main 仍是审批、凭据、审计和确定性执行的权威层。
2. 现有 `Proposal` 与“提议—执行分离”继续服务于 `ASK` 和外部副作用，不再包裹普通工作区 CRUD。
3. 现有 RBAC、Profile、Workflow 和业务复核继续独立存在。
4. 现有 `requireApproval` 与 `autoApprove` 配置必须被实际策略层使用，不能在 UI 中仅展示而不生效。
5. 审批展示契约继续以冻结参数、`summary` 和可选预览为核心。
6. 会话 JSONL 中不再为普通工作区操作生成 `approval_required` / `approval_resolved`。

### 18.1 旧审批配置迁移

当前 `autoApprove`、`requireApproval`、超时和高风险二次确认是 Profile 配置，但现有 Gate 并未完整消费前两项。迁移必须显式映射到 Task Grant 和 Policy Engine，不能保留“配置存在但不生效”的状态。

| 旧配置 | 新语义 |
| --- | --- |
| `requireApproval` | 将匹配的能力从 `ALLOW` 提升为 `ASK`；用于严格模式、外部能力或业务合规，不得把硬拒绝降级为可审批 |
| `autoApprove` | 仅对原本进入 `ASK` 的特定可请求能力应用已批准的自动规则；必须记录规则、原因和自动通过状态，不得覆盖灾难目标、信任锚或凭据隔离 |
| `timeoutMs` | 只作用于需要人工的审批等待；不作用于普通 `ALLOW` 动作 |
| `highRiskDoubleConfirm` | 继续作用于允许审批但需要二次确认的高风险能力；不作用于灾难目标，因为灾难目标是直接拒绝 |

处理顺序固定为：

```text
硬拒绝
  → 信任锚和平台边界检查
  → Task 原生能力
  → requireApproval 提升
  → autoApprove 规则
  → ALLOW / ASK / DENY
```

`autoApprove` 不能把不受沙箱约束、未绑定目标或未通过 Main 语义重算的动作变成自动执行。

### 18.2 Proposal 与时间线迁移

- Standard 模式下普通 Workspace CRUD 产生 `ALLOW`，不创建 Proposal，不产生 `approval_required` / `approval_resolved` 行；
- 只有 `ASK` 创建 Proposal；
- 已获 Task Capability 的外部动作通过 Capability Gateway 执行，写工具时间线和审计，不伪装成文件审批 Proposal；
- Workflow 业务人工复核继续使用自己的事件和页面，不被 `autoApprove` 或 Task Grant 自动通过；
- 对旧会话不回填新语义，历史审批行继续按其原始状态展示。

### 18.3 文档优先级

本设计在“普通工作区操作是否创建 Proposal”“审批触发范围”“Task Grant 与外部能力”三个主题上，取代旧设计中的相反表述：

- `2026-09-06-general-chat-approval-timeline-design.md` 中“所有 bash/edit/write 都先写审批行”的默认入口语义；
- `2026-09-08-approval-render-decoupling-design.md` 中“所有写操作创建提案”的默认入口语义；
- `2026-08-25-general-agent-design.md` 中“写必逐条审批”的默认入口语义。

这些文档中的展示契约、Proposal 冻结原则、RBAC、审计和业务复核仍继续有效。实现设计必须同步修订相关实现计划，避免旧默认行为被重新接线。

## 19. 安全不变量

1. Agent 不得修改自己的 Task Grant。
2. Workspace 之外的访问没有明确授权时不得执行。
3. Task Grant 不得跨任务或跨用户继承。
4. 子 Agent 权限不得大于父 Task。
5. 灾难目标拒绝不能被任何授权覆盖。
6. 外部副作用必须经过 Capability Gateway。
7. 凭据不得进入 Agent Runtime 或工作区进程环境。
8. 平台沙箱不可用时必须失败关闭。
9. 冻结参数或目标变化后原审批失效。
10. 所有自动决策、外部动作和拒绝都必须留审计。
11. 用户主动动作只授权完全匹配的冻结目标与载荷。
12. 恢复能力不得作为普通工作区授权的必要条件。
13. Workspace 未通过 Admission 时不得创建 Task Grant。
14. Trust Anchor 保护优先于 Workspace 普通 CRUD。
15. Capability、目标、风险和用户摘要必须由 Main 从可信定义重新计算。
16. 执行前目标身份或父链变化时，原授权和原审批均失效。
17. Task 撤销必须覆盖新 Action、在途进程、网络连接、Gateway 租约和排队请求。
18. 工作区进程不得通过 IPC、本机服务或宿主自动化接口绕过文件与网络边界。

## 20. 验收场景

### 20.1 标准模式

1. 在工作区创建、修改、移动、重命名和删除普通文件时没有安全弹窗。
2. 删除普通子目录和大量普通文件时没有逐文件审批。
3. 测试、lint、构建和格式化在沙箱内自动执行。
4. 构建工具写系统临时目录时只落到任务私有 scratch 或受控缓存，不触发普通 CRUD 审批。
5. 工具时间线展示执行状态，但没有 `approval_required` 行。
6. 任务结束后能查看结构化文件动作的准确变更清单，以及带来源和限制说明的命令级变更摘要。

### 20.2 越界与外部副作用

1. 读取工作区外目录触发一次清晰的能力请求。
2. 新增网络域名触发一次网络能力请求。
3. 外部系统写在没有预授权时触发外部能力审批。
4. 用户主动点击导出且未改变目标与载荷时不重复安全审批。
5. 用户批准后目标或载荷变化时重新进入策略判定。

### 20.3 灾难保护

1. 删除 Workspace 根本身被拒绝。
2. 删除用户主目录、磁盘根或系统目录被拒绝。
3. 删除 Sparkii 控制目录、审计目录和权限目录被拒绝。
4. 通过符号链接、目录联接或重解析点逃出 Workspace 被拒绝。
5. 通过 Shell 子进程访问工作区外路径被沙箱拒绝。
6. 平台沙箱无法启动时 Standard 不降级为无约束执行。
7. Workspace 等于文件系统根、用户主目录、系统目录、Sparkii 数据目录或其受保护祖先时，Admission 拒绝且不创建 Task Grant。
8. Workspace 内存在 `.env`、Git hook、MCP 配置或受保护插件入口时，普通读取、写入、删除、重命名和 Shell 访问均失败关闭。
9. 批准后目标被替换为符号链接、目录联接、硬链接或重解析点时，执行前身份校验失败。
10. 删除 Workspace 根对象或通过别名触达受保护祖先时被拒绝；普通子项删除仍按 Task Grant 执行。
11. Workspace 位于操作系统目录、平台程序目录或 Sparkii 控制目录后代时，Admission 拒绝且不创建 Task Grant。
12. 用户主目录或普通盘符下的普通项目后代可以通过 Admission，但其祖先链进入受保护闭包根时被拒绝。

### 20.4 多 Agent 与并发

1. 子 Agent 继承但不扩大父权限。
2. 父任务撤销后子 Agent 立即停止获得新授权。
3. 并发修改同一工作区时有写租约或冲突检测。
4. 恢复时检测用户或其他进程的后续修改，不静默覆盖。
5. 父任务撤销时，在途子 Agent 进程树、网络连接和 Gateway 租约被终止。
6. 应用崩溃或重启后，旧 Task Grant、审批认领和外部能力租约不会自动复活。

### 20.5 跨平台一致性

1. Windows、macOS 和 Debian/Ubuntu 对同一 Action 输出相同 Policy 决策语义。
2. 平台路径差异不改变 Task Grant 边界。
3. 平台沙箱不可用时拒绝行为一致。
4. 各平台均通过灾难目标和路径逃逸测试。
5. 沙箱在动作执行中途失效时立即终止动作并失败关闭。
6. 每个 Platform Adapter 返回可验证的能力清单、失败原因和沙箱版本，而不只返回布尔值。

### 20.6 Action 权威与迁移

1. Runtime 伪造工具名、风险、摘要或目标时，Main 仍按可信工具定义重新计算，审批显示与实际执行一致。
2. 批准后载荷哈希、目标身份或父链变化时，执行被拒绝。
3. Standard 模式普通 Workspace CRUD 不创建 Proposal，不产生审批 JSONL 行。
4. `autoApprove` 不能覆盖硬拒绝、信任锚、凭据隔离和平台边界。
5. `requireApproval` 能把指定可审批能力提升为 `ASK`，但不能把硬拒绝改成可审批。
6. Workflow 业务人工复核不被 `autoApprove` 或 Task Grant 自动通过。
7. 旧会话历史审批行按原状态展示，不被新策略回填或改写。

## 21. 成功指标

1. Standard 模式下，工作区内的普通任务审批次数为 0。
2. 越界或外部副作用只在首次申请或参数变化时打断用户。
3. 被拒绝的越界动作执行率为 0。
4. 自动执行审计覆盖率为 100%。
5. 所有审批都能追溯到 Task、Action、规则和载荷哈希。
6. 新连接器、新工具和新平台不修改核心审批 UI 与 Task Grant 语义。
7. 灾难目标和信任锚绕过测试通过率为 100%。
8. 批准后目标身份变化导致的越权执行次数为 0。
9. Task 撤销后新增越界动作数为 0，未终止任务进程数为 0。
10. Standard 模式普通 Workspace CRUD 产生的 Proposal 数为 0，审批 JSONL 行数为 0。
11. 每个自动 `ALLOW` 都能追溯到 Main 重算的资源信息、规则和平台能力自检结果。

## 22. 后续实施设计需要决定的内容

以下内容属于下一阶段实现设计，必须在不改变本文安全语义的前提下确定：

1. Policy Engine 与现有 `ApprovalGate` 的组合方式；
2. Task Grant 的持久化与跨进程传递协议；
3. Windows 首选原生沙箱后端及其兼容性验证；
4. macOS 和 Debian/Ubuntu 的适配顺序；
5. 任务回收区和可选检查点的存储格式；
6. Profile 策略配置 Schema；
7. 审计事件和 UI 状态映射；
8. 迁移现有通用智能体审批配置的兼容方案。
9. Workspace 闭包根和平台受保护目录的机器可读注册表；
10. 路径别名和祖先链准入测试矩阵；
11. Windows 原生沙箱原型验证矩阵，包括 8.3 短名、DOS 设备路径、卷 GUID、UNC、目录联接、硬链接、Alternate Data Stream 和卷别名。
